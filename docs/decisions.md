# Decisions

One entry per decision (an ADR, architecture decision record): the date, the status, what was decided, why, and what would change it. An entry is "proposed" until its pull request is approved by the team (and the client, for scope or hosting), then "accepted". A superseded entry stays, marked with what replaced it.

## ADR-001: Capability-based provider adapters, not a lowest common denominator (2026-10-26, proposed)

Each cloud provider declares the resource types it supports and the canvas shows only those. Why: Patrii has no serverless, API gateway or managed NoSQL table, and a common-denominator model would remove those from AWS users too. Prior art that works this way: Terraform providers, Crossplane compositions, Cluster API providers. Would change if: the client wants one abstract diagram that deploys unchanged to several clouds. Revised 2026-11-13 by ADR-014: diagrams are drawn in building blocks that several clouds share, and each connector still declares what it supports, so this stays capability-based. Revised 2026-10-30: the first cut was a `Provider` interface (`Resources`, `Validate`, `Render`, `Regions`, `Credentials`, `VerifyAccount`, `RunnerEnv`, `StateBackend`; git commit `7b49222`). It became the connector interface in `docs/architecture/system-b-adapter-layer.md`: `Resources` became `Manifest`, `Regions` moved into the manifest, and `Render`, `RunnerEnv` and `StateBackend` moved inside the shared Terraform runner.

## ADR-002: Terraform stays the engine for every provider (2026-10-26, proposed)

Adapters emit HCL for an existing Terraform provider; Clutter does not call cloud APIs to create resources itself. Why: plan, apply, state and drift handling are already solved there, and the runner and logs already speak Terraform. Would change if: a target cloud has no Terraform provider and no OpenStack-compatible API.

## ADR-003: Patrii is targeted through public OpenStack APIs first, its own provider second, and never its console's private API (2026-10-26, proposed)

Why: the standard OpenStack Terraform provider and Keystone application credentials are documented and portable to other OpenStack clouds; Patrii's own provider is not released; the console API is undocumented and changes with each build. Contested: the second research run on the same date recommends coding against the console's REST API now (Path C in `system-b-adapter-layer.md`), since it is the only surface that works today and Patrii's homepage never names OpenStack services. Would change if: Patrii states it will not expose OpenStack endpoints and no provider is planned, or publishes an OpenAPI file and calls its REST API the supported surface.

## ADR-004: A stays SaaS on AWS; B is one container that we host or others self-host (2026-10-26, revised 2026-10-30, proposed)

Why: moving A off Lambda and API Gateway is a separate project, and nothing about Patrii requires it before a Patrii connector works. B1 is by definition a service other people can run, which they cannot do with Clutter's API Gateway and Lambdas, so B is one Go service in a container plus a Terraform runner, hosted by us beside A or self-hosted. Keeping connection credentials and state behind the connector interface leaves room to run the runner inside a customer's cloud. The 2026-10-26 version kept the deployer BYOC-ready through `RunnerEnv` and `StateBackend` on a provider interface; those are now the connection credentials and the runner's state backend. Would change if: the client needs Canadian-only hosting of Clutter itself (data residency, CLOUD Act exposure), in which case hosting on Patrii or BYOC moves before stage 7.

## ADR-005: The central standard is a versioned inbound API over Clutter's own model (2026-10-26, proposed)

Other products, and people, call one `/v1` API. It is B API (ADR-006): it sits beside A's handlers, reuses A's sign-in and organization model, and puts connectors behind it. Its objects, revised 2026-10-30 to follow the team's plan: organization, project, desired state, target, instance, workspace, run, catalog (`docs/architecture/system-b-adapter-layer.md`); revised 2026-11-13 by ADR-014: connection replaces instance in the UI, deployment is added, and workspace is dropped. The 2026-10-26 draft renamed project to workspace; that rename is dropped, because the plan uses workspace for an environment inside an instance. Why: the existing org, project and diagram path with its membership check is sound enough to wrap, while the internal routes are inconsistent (ids in paths and queries, mixed names, no error envelope, no idempotency). Freezing them as the public contract would freeze those gaps. Would change if: the only consumers are Clutter's own frontend, in which case the outbound adapters alone are enough.

## ADR-006: Build B next to A (Option 1), reuse A only at named seams (2026-10-30, proposed)

The adapter layer (B) is new code with its own tests, beside today's AWS system (A), not a rewrite of A. B touches A at four named seams only: the UI target choice, shared sign-in and the JWT authorizer, the shared database (a target field on projects, new target, instance and credential tables), and the security fixes on paths B shares with A. Reusing other A code (Option 2) is the fallback and is decided case by case. Turning A into the adapter (Option 3) is a later destination reached piece by piece, never the first move. Why: A is a complete, tested application, and every change to it means retesting every AWS path. Source: the team's plan in `docs/architecture/system-b-team-plan/`. Trade-off: B duplicates some of A (job tracking, logs) until AWS moves into B. Would change if: B needs so much of A that the duplicated code costs more than A's retest would. Revised 2026-11-13 by ADR-014: B adds deployments instead of a target field on projects, reads A's linked AWS roles, and reuses A's templates for its AWS connector; A's own code changes only where stage 1 makes it shareable: its template loader and JWT check move into `generic`, and the generator reads the environment's region (`docs/architecture/implementation-plan.md`). The UI seam is now B's own editor and Connections page, chosen per diagram, not a target choice on A's screens.

## ADR-007: B0 (SaaS) first, then B1 (self-hosted), then B2 (internal) (2026-10-30, revised 2026-11-08, proposed)

Revised 2026-11-08: B0, B run by us as a hosted service, comes first, because it proves B with the least setup and support work; B1 follows when a customer asks to run Clutter on their own servers. B stays portable (any Postgres, any S3-compatible store) so B1 remains possible. B1 needs nothing we do not have. B2 needs to know how targets such as TierHive and PatriCloud run inside the companies that use them. Build order: connector interface, the B skeleton run as B0, and General; then PatriCloud and TierHive; then B2. Would change if: a partner hands over the details B2 needs, or the client wants B2 first. Revised 2026-11-13: the full order, General's OpenStack connector, then B's AWS connector, then the rest, is the stages in `docs/architecture/implementation-plan.md`. B1 is later; B2 is later still, and whether to do it at all is a separate decision.

## ADR-008: General comes first, and covers targets without an API (2026-10-30, proposed)

General has two modes: Terraform with a provider the connection names, and existing hosts over SSH with Ansible. Revised 2026-11-13: the provider comes from an allow-list Clutter maintains, OpenStack first (ADR-014, ADR-017). General is a family: one connector per approved provider (`general-openstack`, later `general-digitalocean`) plus one for existing servers (`general-ssh`), sharing one kit, and users pick a cloud by name. A new cloud reachable through an approved Terraform provider is a new General connector, so Patrii's OpenStack endpoints or its own provider, and a future TierHive provider, arrive through General; a cloud gets a named connector of its own only when no approved provider reaches it or Clutter must drive its own sign-in flow (AWS, Patrii's console API). Why: it needs no partner, and it is the only way to reach TierHive and Patrii today, since neither has a public API (`docs/research/tierhive/2026-10-30-tierhive-research.md`, `docs/research/patricloud/2026-10-26-patricloud-research.md`). Would change if: the client defines General differently.

## ADR-009: A local dev gateway runs System A without AWS (2026-10-30, proposed)

`backend/devserver` runs A's real, unchanged Lambdas on one machine: a gateway on loopback that stands in for API Gateway and the authorizer, Postgres in Docker, and a dev-only sign-in. It never ships and never deploys. It refuses to start with a secret it did not generate, a non-loopback address or a non-loopback database, and every AWS call is refused locally. It has its own Go module, so A's `go.mod` is untouched, and a test fails if its route table drifts from `backend/infra/main.tf`. B's local development reuses it rather than adding a second launcher. Why: A was built to run only in AWS, the capstone account is gone, and deploying A as it is would expose the open security defects; this is the only way to check A, and the seams B touches, without an account or cost. Trade-off: about 2,900 lines of tooling to maintain, and it can differ from real API Gateway (request-model validation is not applied). Would change if: we get a dev AWS account and a deploy pipeline that make a local run unnecessary, or the gateway's behaviour drifts from API Gateway in a way that misleads.

## ADR-010: Three environments: local, dev and prod, sharing nothing (2026-11-04, superseded by ADR-015)

Clutter runs in three places with one job each: local (each developer, no accounts), dev (the team's real-cloud proof) and prod (customers). The same code runs in all three and only configuration differs. They share no AWS account, database, Google client, secret or state bucket, and change moves one way, from local through `main` and dev to prod. `docs/architecture/environments.md` holds the table. Why: a mistake in dev must be unable to touch prod, and the team needs one clear answer to "what is different where". Trade-off: two sets of accounts to look after. Would change if: the client wants one AWS account with separate stacks to save cost, which is weaker isolation.

## ADR-011: C is A + A2 + B; A2 extends A without changing it (2026-11-04, proposed)

The whole app, C, has three parts. A is Clutter as built. A2 is the extension that makes A run and test without AWS (`backend/devserver`), by answering the outside calls A makes rather than editing A. B is the adapter layer. New local and test abilities go in A2. A itself changes only for security and bug fixes and for small named seams (ADR-006). Why: A stays exactly as delivered and every change stays easy to see, and it replaces a proposal to rework all 33 handlers, which would have changed all of A at once. Trade-off: A2 depends on A's internals, such as which AWS calls it makes, so a change in A can break it. One exception, chosen by the person: the **Link fake account** button sits in A's frontend, shown only in a development build with a loopback API, because it is the one way to unlock the canvas for a Google sign-in locally. Would change if: A2 keeps breaking when A changes, or customers need to run A2 themselves, which would make it a shipped product.

## ADR-012: Reading generated Terraform is a product feature of A (2026-11-04, accepted)

Every user with a linked account, in every environment, can read and download the Terraform for a saved diagram, in the editor. One new authenticated route reads what A's real generator wrote, and the generator records a status beside the files, so the editor can warn when the files are from an older save. It is an agreed exception to ADR-006: a new feature in A, plus a small change to the generator. The editor panel comes from a teammate's `feat/local-terraform-preview` branch; that branch's separate disk generator is not used, so what users see is always what A produces. Why: a user should see the code that will run in their account, and A offered no way to do that. Trade-off: it depends on generation working, so in cloud it needs the Supabase webhook and phase 0 item 1. Would change if: users need a preview before saving, which needs generation on demand.

## ADR-013: Clutter is one hosted product where users bring their own cloud accounts (B0 + 2.1) (2026-11-13, proposed)

Clutter is run by us as SaaS (B0), and diagrams build in the user's own cloud accounts, which they link on a Connections page (world 2.1), in the way Brainboard works. Clutter-managed accounts, where Clutter owns the clouds users build in and bills them (2.2), are not in scope. Live multi-user collaboration is built by another team on top of this work; we keep the diagram document stable for them. Why: 2.1 is what A already does for AWS, and 2.2 is a different business (we would pay every user's cloud bill and need billing, abuse limits and liability cover) that adds nothing to the adapter layer. Would change if: the client wants to resell cloud capacity. Revised 2026-11-13: a narrow form of 2.2 may come later as an optional "use Clutter's sandbox" connection, into a separate Clutter-owned account (never the account Clutter runs in), with a per-user spending cap and automatic clean-up; connections are designed so it is one more connection type.

## ADR-014: One diagram, many deployments, and AWS as a B connector too (2026-11-13, proposed)

A diagram is drawn once in building blocks (VM, network, firewall, volume, bucket, function, table, HTTP API) and can be deployed to several linked clouds. Each deployment is the diagram bound to one connection, with its own settings, state and runs; the capability check shows per deployment what that cloud cannot build. AWS joins B as a connector that reuses A's customer templates and role link, so a new diagram can deploy to AWS beside other clouds; A stays unchanged and keeps serving existing AWS diagrams until B's AWS connector covers it. General's first connector is OpenStack (`general-openstack`), tested on DevStack, which is also Patrii's Path A. Why: choosing one cloud per diagram is poor for users, and per-target diagrams would need to be redrawn for every cloud; reusing A's templates keeps the AWS Terraform in one place. Trade-off: AWS is reachable through two paths until A's flow retires, and building blocks need a mapping per connector. Not in the first build: one diagram spread across several clouds, because edges across clouds cannot carry permissions. Replaces "target-native nodes first" in ADR-001's design and the project target field in ADR-006. Would change if: the client wants each diagram tied to one cloud, or the block mappings prove too lossy for real diagrams. Revised 2026-11-13 after an independent review and a code check: A's template-loading code moves out of its `internal` package into `generic` so B can import it, guarded by a golden test that keeps A's output byte-identical; B has its own edge-to-IAM step; the AWS role template trusts both A's and B's runner roles, and each connection records its role-template version; a building-block diagram carries `engine: "blocks"` and A's generation skips it; a deployment can leave out a block its cloud cannot build; blocks are addressed by node id and cloud names carry a deployment prefix; a connection, diagram, project or organization with live deployments cannot be deleted until they are destroyed.

## ADR-015: Two environments: local and one cloud, run with prod rules, in ca-central-1 (2026-11-13, proposed; supersedes ADR-010)

Clutter runs locally (each developer, no accounts) and in one cloud environment in the client's AWS account in `ca-central-1`, deployed with `npm run deploy -- prod`: only from a clean `main`, with a typed confirmation and no tear-down command. Diagrams in the cloud deploy into our own test accounts: a second AWS account acting as a user, and an OpenStack (DevStack on a virtual machine, switched on for demos) until Patrii opens. Why: there are no outside users yet, all testing happens locally and in CI, and one set of accounts is simpler for the client and the team; a Canadian region suits a Canadian product. Trade-off: a risky change has nowhere to be tried in a real cloud before it is live. Would change if: real outside users arrive, which adds a separate test environment (the deploy command already takes the environment as a parameter).

## ADR-016: User cloud credentials: borrowed where possible, otherwise an encrypted secret, never a password (2026-11-13, proposed)

AWS keeps A's model: a role the user creates, short-lived keys at each run, nothing permanent stored. Other clouds use the most limited credential they offer (an OpenStack application credential, an API token, an SSH key), stored in AWS Secrets Manager in B0, one secret per connection, with only its reference in Postgres; locally A2 encrypts it with a key from its own config. The runner reads it for one run and never logs it. Deleting a connection deletes its secret. Why: Clutter holds access to other people's clouds, so a leak must expose as little and as briefly as possible. Would change if: B1 is built, where the customer's own secret store takes this place.

## ADR-017: Each run is isolated; only Clutter writes the Terraform it runs (2026-11-13, proposed)

B starts one short-lived task per run, with no database or secret-store access; a broker in B's API hands it only that run's credentials (short-lived session keys for AWS, the one connection's token otherwise). B renders all Terraform from building blocks with its own templates; General supports only providers on an allow-list Clutter maintains, not any provider a user names; rendered Terraform with provisioners or the `external` or `http` data sources is refused before `plan`; `TF_LOG` is never set; B's run tasks use their own cluster. Why: a runner holds the keys to a user's cloud. A's runner today can assume every customer's role and is handed the database string that holds every external id, so a single injected command reaches every tenant (found by the 2026-11-13 review; added to phase 0). Trade-off: General is narrower than "any Terraform provider", and each run pays a container start. Would change if: a provider is needed that cannot be allow-listed, in which case it runs in its own isolated runner.
